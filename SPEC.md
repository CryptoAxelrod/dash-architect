# SPEC.md — техническая спецификация Dash Architect

Статус: скелет. Зафиксировано то, что можно однозначно вытащить из демо-макета
(`/reference`) — токены, композиция, структура разделов. Правила классификации столбцов,
состав тем и детали экспорта будут уточнены отдельными промптами; здесь для них оставлены
явные заглушки, чтобы структура документа не менялась, когда придут детали.

Правила, которым подчиняется реализация всего описанного здесь, — в [CLAUDE.md](CLAUDE.md).

---

## 1. Обзор

Dash Architect — надстройка Excel, которая по выделенной таблице детерминированно строит
дашборд: KPI-карточки, график, таблицу и фильтры/переключатели. Демо-макет в `/reference`
задаёт визуальный язык и композицию продукта, но сам не содержит рабочей логики (любой выбор
в панели ведёт к одному и тому же заранее подготовленному дашборду).

Из демо взяты две поверхности интерфейса:

- **Панель настройки** (`reference/taskpane.html` + `.css` + `.js`) — task pane сбоку от листа,
  где пользователь выбирает диапазон и компоненты дашборда.
- **Сам дашборд** (`reference/dashboard.html`) — самодостаточная HTML-страница (разметка +
  стили + скрипт в одном файле), которая одновременно является Excel content add-in,
  вставляемым на лист.

## 2. Структура репозитория

См. [CLAUDE.md](CLAUDE.md#структура-репозитория). Кратко: `/engine` (детерминированная логика,
чистый Node), `/addin` (Office.js интеграция), `/render` (структура данных → DOM/SVG),
`/fixtures` (тестовые таблицы), `/tests` (снапшоты), `/reference` (демо-макет, не часть
продукта).

значениях. Это зафиксировано как есть, а не сглажено — сведение в единый набор токенов
потребует отдельного решения.

### 3.2 Типографика

- Шрифт: **Archivo**, вариативный (оси `wdth` 62–125, `wght` 400–800), через Google Fonts.
  Фолбэк: `"Segoe UI", "Helvetica Neue", Arial, sans-serif` (панель) /
  `"Helvetica Neue", Arial, system-ui, sans-serif` (дашборд).
- Числовые значения почти всегда с `font-variant-numeric: tabular-nums`.
- Заголовки используют не только `font-weight`, но и `font-stretch` (растяжение вариативного
  шрифта) плюс отрицательный `letter-spacing` — это часть визуального почерка, не случайность.

Зафиксированные размеры (панель):

|---|---|---|---|---|

| `.tagline` | 13.5px | — | — | — |
| `.step h2` | 15.5px / lh 1.3 | 650 | 108% | — |

### 3.3 Радиусы и форма

Наблюдаемая шкала скруглений: `4px, 5px, 6px, 7px, 8px, 9px, 10px, 12px`, плюс `999px` для
полностью скруглённых пилюль (сегментированные переключатели, чипы, свитчи). Явной "шкалы" из
2–3 значений в демо нет — радиус подобран на глаз под размер элемента; при формализации
токенов это стоит либо принять как есть (много значений), либо сознательно сжать в шкалу.

### 3.4 Отступы и сетка

- Панель: боковые поля контента `18px`; шаг (`.step`) — сетка `24px` (колонка иконки) +
  `12px` gap; карточки компонентов — grid 2 колонки, `gap: 8px`; отступ карточки
  `10px 10px 9px`; sticky-футер `12px 18px 16px`.
- Дашборд: контейнер `max-width: 1180px`, поля `34px 28px 52px`; grid обзора (KPI + график)
  — `minmax(0,5fr) minmax(0,7fr)`, `gap: 44px`; чипы категорий — `gap: 8px`; панель
  (`.panel`) — отступ `18px 20px`, радиус `12px`.
- Брейкпоинты: `880px` (grid обзора → 1 колонка, KPI hero уменьшается до 52px) и `540px`
  (поля контейнера `22px 16px 40px`, KPI-строка → 2 колонки, `.kpi-row .kpi-value` → 24px,
  таблица получает горизонтальный скролл через отрицательные поля `-14px`).

### 3.5 Состояния и интеракция

- Фокус: `outline: 2px solid var(--green); outline-offset: 2px` — единообразно на обеих
  поверхностях.
- `prefers-reduced-motion: reduce` отключает все анимации и transition — обязательный кейс,
  не декоративная деталь.
- Анимации — короткие (`.15s`–`.5s`), `cubic-bezier(.2,.7,.3,1)` для "роста" элементов
  (бары графика, превью карточек), линейные для прогресс-заливки кнопки генерации.

## 4. Композиция панели настройки (task pane)

Источник: `reference/taskpane.html/.css/.js`, скриншоты 1–2.

- **Шапка/бренд**: SVG-иконка (32×32, скруглённый прямоугольник с мини-пиктограммой
  дашборда) + заголовок "Dash Architect" + тэглайн. Фон шапки — едва заметная сетка
  "worksheet grid", проявляющаяся справа через градиентную маску.
- **Вертикальный степпер из 2 шагов**, соединённых тонкой рейкой (`rule`):
  1. **Choose your data** — компонент выбора диапазона (`refedit`) с тремя состояниями:
     - `empty` — плейсхолдер "No range yet" + кнопка "Select range".
     - `picking` — анимированная пунктирная рамка ("marching ants"), кнопка меняется на
       "Done", подсказка снизу "Select cells in the sheet, then press Done."; адрес
       диапазона обновляется вживую по мере выделения.
     - `set` — показан адрес ячеек и лист отдельно, кнопка "Change"; ниже — число строк/
       столбцов и горизонтальная лента найденных заголовков (первый заголовок подчёркнут
       акцентным цветом; если заголовков нет — сообщение о том, что первая строка будет
       считаться данными).
  2. **Pick components** — сетка 2×2 карточек-чекбоксов (KPI cards / Chart / Table /
     Toggles). Каждая карточка: заголовок с чекбоксом, мини-превью в виде "чертежа" (dashed
     SVG-скетч), которое при выборе анимированно "достраивается" в закрашенный превью с
     реальными на вид значениями, и подпись-описание снизу. Счётчик "N of 4" рядом с
     заголовком шага.
  - Каждый шаг получает визуальную отметку "done" (кружок с номером превращается в
    закрашенный кружок с галочкой), когда его условие выполнено (диапазон выбран /
    хотя бы один компонент отмечен).
- **Sticky-футер сборки** (шаг 3, без номера в самой структуре степпера выше, но
  пронумерован как "3"): текстовое саммари выбора, большая кнопка "Generate dashboard" с
  анимацией заливки прогресса и сменой подписи по "фейковым" этапам сборки
  (`Reading N rows… → Calculating KPI cards… → Drawing the chart… → ... → Placing it on a
  new sheet…`), состояние ошибки (текст под кнопкой), и состояние "готово" — иконка успеха,
  заголовок, подпись с судьбой листа, две кнопки ("Open dashboard" / "Start over").
- Скрытый (не документированный в UI) сброс демо — двойной клик по логотипу.

## 5. Композиция дашборда

Источник: `reference/dashboard.html`, скриншот 3.

- **Заголовок**: `h1` с названием дашборда (в демо — "Store sales, 2025") + `.lede` —
  автосгенерированное предложение-саммари (число записей, период, число категорий) +
  сегментированный переключатель периода (Full year / Q1–Q4) справа.
- **Чипы категорий**: горизонтальный ряд пилюль, первая — "All categories" (сброс фильтра),
  остальные — по одной на значение категориальной колонки; активная выделена заливкой.
- **Overview**: двухколоночная сетка (5fr/7fr на десктопе, 1 колонка на ≤880px):
  - Левая колонка — KPI-блок:
    - Hero-KPI (крупнейший): подпись, огромное значение, короткое пояснение
      (например, "Avg $719 per transaction").
    - Разделительная линия, затем строка из 3 вторичных KPI (разделены вертикальными
      линиями), каждый — подпись/значение/пояснение.
  - Правая колонка — панель графика: заголовок (меняется в зависимости от выбранной
    метрики и периода, например "Margin by month"), сегментированный переключатель
    метрики (Sales / Profit / Margin), и сам график — **вручную собранный inline SVG**
    (столбчатая диаграмма): ось Y с "красивыми" шагами сетки, подписи по X с прореживанием
    под ширину, столбец-пик визуально выделен и подписан значением, hover/focus по
    столбцу показывает всплывающую подсказку (`.tip`) с разбивкой по продажам/прибыли/
    марже/числу транзакций.
- **Таблица**: заголовок с числом строк, поиск (по категории/дате) и переключатель
  "Losses only"; сортируемые заголовки колонок (клик — направление сортировки, стрелка-
  индикатор); строки с числовыми колонками через `tabular-nums`, колонка маржи — инлайн
  мини-бар (пропорциональная заливка) + процент; строка итогов (`tfoot`, жирная, с более
  толстой верхней границей); пагинация — выбор строк на страницу, "Previous"/"Next",
  текст диапазона ("X–Y of Z"); пустое состояние при отсутствии совпадений.

## 6. Модель данных

*Скелет — детали формата и парсинга будут уточнены отдельно.*

Вход в `/engine`:
- Сырые данные листа как массив массивов (`values[row][col]`), включая заголовок(и), если
  есть.
- Метаданные форматов ячеек (Excel number format строки) — по колонкам и/или по ячейкам —
  нужны, чтобы отличать, например, дату от числа, процент от доли, текст от числового ID.

Открытые вопросы (детали придут позже):
- Как определяется наличие/отсутствие строки заголовков.
- Каноническое внутреннее представление строки/колонки после парсинга (типы значений,
  обработка пустых ячеек, многострочные заголовки — см. `fixtures/06_messy_headers.csv`).
- Разбор локализованных чисел/дат (например, `07.04.2024`, `925 408,28`, `48,5%` —
  см. `fixtures/07_ru_locale_text_numbers.csv`) — реализуется вручную, без зависимостей
  (правило из [CLAUDE.md](CLAUDE.md#4-зависимости--по-умолчанию-ноль-любое-добавление-обсуждается)).

## 7. Роли столбцов

Реализовано в [`engine/roles.js`](engine/roles.js). Пять ролей:

| Роль | Смысл | Агрегация |
|---|---|---|
| `time` | ось времени | — |
| `dimension` | разрез/фильтр | — |
| `measure` | метрика | `sum` \| `avg` \| `weighted` |
| `text` | только в таблицу, не участвует в агрегатах | — |
| `excluded` | не похоже на данные для дашборда (идентификатор, пустая колонка) | — |

Каждое решение — объект `{role, aggregation, confidence, rule, reason, ...}`, где `rule` —
слаг правила, которое сработало (`format_date`, `identifier`, `year_like`, `fraction_like`,
`per_unit`, `low_cardinality`, `default_measure`, `default_text`), а `reason` — фраза на
английском для интерфейса (см. `engine/playground.html`). Для `measure`/`weighted` решение
также несёт `needsWeightBase` и, если пара найдена, `weightBase: {numerator, denominator}`
(см. §8).

`confidence` — три уровня, привязанные к номеру правила, а не к "расстоянию" до порога:
`high` (правило 1, формат ячейки), `medium` (правила 2–5, именные и диапазонные эвристики),
`low` (правила 6–8, дефолты). Осознанное упрощение: подробнее в §8.

В `/fixtures` уже заложен корпус кейсов, которые правила классификации обязаны различать
(имена файлов — рабочие названия кейсов, не финальная терминология ролей):

- `01_sales_timeseries` — временной ряд с явной датой.
- `02_no_time_dimension` — данные без временного измерения вовсе.
- `03_numeric_id_traps` — числовые колонки, которые на самом деле идентификаторы
  (Order ID, SKU, Postal Code, Store No, Year, Warehouse Bay), а не измерения.
- `04_percent_with_base` — доля/процент, для которой есть колонки-основания (Impressions,
  Clicks и т.п.), из которых её можно пересчитать.
- `05_percent_without_base` — доля/процент без колонок-оснований в данных.
- `06_messy_headers` — таблица с "шапкой отчёта" перед настоящей строкой заголовков.
- `07_ru_locale_text_numbers` — русская локаль: `;`-разделитель, дробная запятая,
  пробел как разделитель тысяч, проценты как текст со знаком `%`.
- `08_text_heavy` — таблица с преимущественно текстовыми/свободными колонками (тикеты,
  email, тема обращения).
- `09_wide_many_measures` — широкая таблица с большим числом числовых измерений.
- `10_large_volume` — большой объём строк (нагрузочный кейс, не про классификацию).

## 8. Правила определения ролей

Реализовано в [`engine/roles.js`](engine/roles.js), пороги — в объекте `CONFIG` наверху
того же файла (не разбросаны по коду). Правила проверяются строго по порядку, первое
сработавшее выигрывает:

1. **Формат ячейки.** Дата → `time`. Процент → `measure`/`weighted`. Валюта → `measure`/`sum`.
   Текстовый формат на числовом столбце (например, номер с ведущим нулём, сохранившимся
   только потому, что ячейка — текст) → кандидат в `dimension`. Формат важнее любой
   эвристики по имени ниже.

   CSV не несёт настоящих Excel-форматов ячеек, поэтому для CSV-источника (используется
   `engine/playground.html`) формат *выводится* из самого текста: явный `%` в значении —
   это и есть "процентный формат"; число с ведущим нулём (`00512`) — сигнал "отформатировано
   как текст". Когда движок научится читать реальные `.xlsx`, эта эвристика в
   `engine/values.js` заменится/расширится настоящими форматами ячеек — остальной конвейер
   (`profile.js`, `roles.js`) от источника формата не зависит.

2. **Похоже на идентификатор.** Целые с уникальностью > 95% ИЛИ имя содержит одно из
   `id, код, артикул, номер, №, sku, индекс` (подстрокой, без учёта регистра) → `excluded`.
   Список ключевых слов — буквально то, что задано в промпте, без добавления синонимов
   (`code`, `no`, `number`) — расширять осознанно, отдельным изменением с обновлением
   снапшотов, а не по ходу дела.
3. **Похоже на год.** Целые в `[1900, 2100]`, уникальных < 50 → `time`, `granularity: 'year'`.
4. **Похоже на долю.** Дробные в `[0, 1]` — без требования к имени; ИЛИ значения в
   `[0, 100]` **и** имя содержит одно из `%, процент, доля, конверсия, маржа, rate, share,
   ratio` → `measure`/`weighted`, `needsWeightBase: true` (до попытки найти базу — см. ниже).
5. **Похоже на удельную величину.** Имя содержит `цена, стоимость за, средн, на единицу,
   per` → `measure`/`avg`.
6. **Низкая кардинальность.** Только для нечисловых столбцов: уникальных ≤
   `min(25, 5% от числа строк)` → `dimension`.
7. **Остальные числа** → `measure`/`sum`.
8. **Остальной текст** → `text`.

Пустая колонка (все значения пустые) — отдельная проверка перед правилом 1: `excluded` с
причиной "нет данных", а не попытка угадать роль по нулевой информации.

### Взвешенные проценты: поиск базы

Для каждой `measure`/`weighted` колонки (`needsWeightBase: true`) движок ищет пару
числитель/знаменатель среди **всех** числовых столбцов таблицы (независимо от их
собственной роли — например, `Impressions`/`Clicks` в `04_percent_with_base` сами
классифицируются как `excluded` по правилу 2, но остаются годным основанием для `CTR`).

Порядок поиска — `engine/roles.js`, `CONFIG.weightBase.hints` + полный перебор:
1. Подсказки по имени (конверсия ← заказы/визиты, маржа ← прибыль/выручка, CTR ← клики/
   показы и т.п.) пробуются первыми, чтобы не перебирать все пары вслепую.
2. Каждая кандидатная пара проверяется **численно**, построчно: `numerator[i] / denominator[i]`
   должно совпадать со значением взвешенного столбца с точностью `±0.5 процентных пункта`
   (абсолютный допуск на шкале 0–1, не относительный — относительный 0.5% ломается на
   малых процентах из-за банального округления исходных данных, это подтвердилось на
   `04_percent_with_base.csv`: `CTR` округлён до 4 знаков, и на части строк относительная
   ошибка от одного округления превышает 0.5%).
3. Пара принимается **только** если проверка прошла на всех сравнимых строках (их не меньше
   `CONFIG.weightBase.minComparableRows`). Совпадение имён само по себе ничего не решает —
   это лишь порядок перебора, не основание для записи пары.
4. Если пара нашлась — `weightBase: {numerator, denominator}`, `needsWeightBase: false`.
   Если нет (как в `05_percent_without_base.csv`, где базовых колонок в данных просто нет,
   или `OEE`/`Availability` в `09_wide_many_measures.csv`, где готовой пары для деления
   действительно нет) — `weightBase: null`, `needsWeightBase: true` остаётся как есть.
   Ничего не подставляется молча.

### Наблюдения по фикстурам (не баги, а свойства буквального применения правил)

Прогон правил на `/fixtures` вскрыл несколько пограничных случаев, которые стоит иметь в
виду при появлении следующих правил или при работе с реальными данными:

- `Store No` и `Warehouse Bay` (`03_numeric_id_traps`) не похожи на идентификатор ни по
  уникальности (низкая), ни по имени (ключевые слова не совпадают), и остаются числовыми —
  поэтому правило 6 (только для нечисловых) их не подхватывает, и они попадают в
  `measure`/`sum` по правилу 7, хотя семантически это, скорее, разрезы.
- `Impressions`/`Clicks` (`04_percent_with_base`) — большие целые с почти 100% уникальностью
  → срабатывает правило 2 (идентификатор), хотя это полноценные метрики. Для поиска базы
  взвешивания это не мешает (см. выше), но как отдельные колонки дашборда они были бы
  исключены.
- `Avg Unit Price` (`01_sales_timeseries`), `CPC` (`04_percent_with_base`) — по смыслу
  удельные величины, но их английские названия не содержат ни одного слова из списка
  правила 5 (список дан на русском + `per`) → попадают в `measure`/`sum` по правилу 7.

Это не ошибки реализации — правила применены буквально, как заданы. Список ключевых слов в
правилах 2/4/5 стоит explicitly расширить (в первую очередь англоязычными синонимами), когда
дойдёт очередь — с обновлением снапшотов, как того требует
[CLAUDE.md](CLAUDE.md#6-изменение-правил-классификации-столбцов--обновление-снапшотов).

Тестовый стенд: [`engine/playground.html`](engine/playground.html) — загружает CSV в
браузере (без сборки, без сети) и показывает результат работы правил 1–8 и поиска базы по
каждому столбцу.

Снапшот-тесты — [`tests/classify.test.js`](tests/classify.test.js), один тест на **каждый**
файл в `/fixtures` (список читается динамически, `fs.readdirSync`, а не захардкожен — новая
фикстура автоматически получает тест при первом прогоне с `UPDATE_SNAPSHOTS=1`). Это включает
`06_messy_headers.csv` (детекция строки заголовков ещё не реализована — весь файл схлопывается
в один текстовый столбец, и это ровно то, что зафиксировано в снапшоте: не "правильный"
результат, а текущее поведение) и `10_large_volume.csv` (60k строк, отдельная лёгкая проверка
таймига дополняет снапшот, не заменяет его). Запуск — `npm test`, одна команда. При расхождении
падает только сравнение конкретной фикстуры, и сообщение об ошибке — не дамп всего объекта, а
список разошедшихся столбцов с тем, что именно поменялось (`tests/lib/classify-snapshot.js#diffColumns`/`formatDiff`), например:

```
01_sales_timeseries.csv — 1 column(s) diverged from the snapshot:
  Margin: aggregation "weighted" → "avg", rule "fraction_like" → "per_unit", weightBase {...} → null
```

Обновление снапшотов после осознанного изменения правил/порогов:
`UPDATE_SNAPSHOTS=1 node --test tests/classify.test.js`, затем `git diff tests/snapshots/` —
чтобы увидеть именно то, что должно было измениться, и ничего сверх этого.

## 10. Состав дашборда

Реализовано в [`engine/layout.js`](engine/layout.js). Композиция выводится из ролей столбцов
(§7) механически — один и тот же алгоритм для любой входной таблицы, никаких датасет-
специфичных веток:

| Блок | Правило | Кап |
|---|---|---|
| Полоса фильтров | один контрол на каждый `dimension` | первые 5 по порядку столбцов, остальные — счётчик "+N more" |
| KPI-карточки | одна на каждый `measure` | первые 6 по порядку столбцов; первая — hero (крупная), остальные — вторичные, разделены вертикальной чертой (без рамок — как в демо, где `.kpi-row` тоже без своих боксов) |
| Линия | если есть `time`-столбец и хотя бы один `measure` | ровно 0 или 1 |
| Столбчатые графики | по одному на каждый `dimension` с `uniqueCount ≤ 12` | вместе с линией — не больше 4 графиков суммарно; при нехватке слотов побеждают более ранние по порядку столбцов |
| Таблица | все столбцы, кроме `excluded`, всегда одна | — |

Все графики строятся по **одной и той же "главной метрике"** — первому `measure`-столбцу по
порядку — а не по разным метрикам на разных графиках; это буквально то, что означает
"главная метрика" в исходном ТЗ.

**Компоновка — это координаты, не CSS.** `engine/layout.js` — не набор классов и не грид;
это буквально функция `buildLayoutSpec(analysis) -> {canvas:{width,height}, widgets:[...]}`,
где у каждого виджета уже есть `rect: {x,y,w,h}` в пикселях, посчитанный один раз. Оба
рендерера (§13) рисуют виджет по этому rect и никогда не пересчитывают позиции сами — это и
есть смысл фразы "движок компоновки выдаёт `layoutSpec`" из исходного ТЗ: раскладка решена
до рендера, а не во время него.

**Фильтрация не двигает виджеты.** `engine/layout.js#recompute(analysis, widgets, {activeFilters, sort})`
берёт тот же список виджетов (те же `id`/`type`/`rect`) и просто пересчитывает их данные по
отфильтрованному подмножеству строк — состав и расположение блоков зафиксированы на этапе
`buildLayoutSpec`, взаимодействие с фильтрами их не меняет. Агрегация (`engine/aggregate.js`)
учитывает способ агрегации метрики (§8): `sum`/`avg` — прямое суммирование/среднее;
`weighted` с найденной базой — сумма числителя делённая на сумму знаменателя по
отфильтрованным строкам (не среднее готовых процентов); `weighted` без базы — среднее по
строкам с флагом `approximate: true`, который обе поверхности обязаны показать явно
(подпись "Unweighted average — no verified weight base" вместо обычной), а не скрывать.

**Наблюдение**: `Store No`/`Warehouse Bay` (см. §8) остаются `measure` и получают KPI-
карточки/попадают в таблицу как метрики, а не разрезы — прямое следствие правила 6,
задокументированного там же.

## 11. Темы

Реализовано в [`render/themes.js`](render/themes.js) — четыре темы, `light` (дефолт), `dark`,
`report`, `print`. Тема — это исключительно объект токенов
(`color`, `font`, `spacing`, `radius`, `card`, `table`, `type`, `chart`); ни один рендерер не
проверяет `theme.id`, чтобы поменять состав или расположение виджетов — только чтобы выбрать
значение токена. Один и тот же `layoutSpec` рисуется всеми четырьмя без изменений.

- **`light`** — палитра и типографика взяты из `reference/dashboard.html` без изменений
  (см. §3.1). Дефолт.
- **`dark`** — не инверсия `light`: свой тёмный, зеленовато-угольный фон (не нейтральный
  чёрный), текст и акцент пересчитаны под контраст на тёмном, серия графиков — свои цвета
  (светлее и менее насыщенные, чем в `light`, чтобы не "выжигать глаза").
- **`report`** — белый фон, `card.style:'flat'` (тонкая линия-разделитель вместо рамки/тени
  панели — у графика/таблицы; KPI и так без рамок во всех темах, см. ниже), уменьшенная
  типографика и отступы, меньшая высота строки таблицы → на том же пикселе таблицы
  умещается больше строк ("больше данных на экран").
- **`print`** — `chart.textures: true`: серии/сектора заливаются SVG-паттерном
  (штриховка/точки/сетка через `<pattern>`), точки линии получают маркеры разной формы
  (circle/square/triangle/diamond), линии могут получать разный `stroke-dasharray` — так
  графики читаются в чёрно-белой печати и людьми с нарушением цветовосприятия, а не только
  по цвету. Отрицательные числа — не цветом, а бухгалтерскими скобками (`(123)`), токен
  `theme.negativeStyle: 'parens'` (остальные темы: `'color'`, минус + `--negative`).

**Важное отклонение от демо**: шрифт везде — системный стек
(`"Segoe UI", "Helvetica Neue", Arial, system-ui, sans-serif`), не `Archivo`. `Archivo` в
демо грузится с Google Fonts, а `/render` не должен зависеть от сети ради того же, ради чего
CLAUDE.md запрещает это в `/engine`/`/addin`: результат обязан быть предсказуем пиксель-в-
пиксель, а исход сетевого запроса к шрифту — нет.

**KPI никогда не в рамке.** Это не токен per-theme, а инвариант из демо: в
`reference/dashboard.html` `.kpi-row`/`.hero` не имеют своего бокса/тени ни при каких
обстоятельствах — только текст и разделительные линии между вторичными карточками. Только
`chart`/`table` виджеты проверяют `theme.card.style` (`'panel'` — рамка+радиус, как в демо, у
`light`/`dark`; `'flat'` — только нижняя линия, у `report`/`print`).

## 12. Рендер: `layoutSpec` → две поверхности

Реализовано в `/render`: [`svg.js`](render/svg.js), [`dom.js`](render/dom.js),
[`format.js`](render/format.js) (общее форматирование чисел/процентов/валют — общее, чтобы
число выглядело одинаково в обеих поверхностях), [`themes.js`](render/themes.js).

- **SVG-рендерер** (`render/svg.js`) — чистая сборка строки: `renderDashboardSvg(layoutSpec, theme, columnsByName) -> "<svg>...</svg>"`.
  Ни одного обращения к DOM/browser API — весь файл может выполняться и в Node. Ручная
  геометрия для всех 5 типов графика (см. ниже), без графических библиотек
  ([CLAUDE.md](CLAUDE.md#5-никаких-графических-библиотек--только-svg-руками)).
- **DOM-рендерер** (`render/dom.js`) — `mount(container, analysis, theme, meta) -> controller`.
  Интерактивные части (фильтры, сортировка/пагинация таблицы, тема) — обычные DOM-узлы с
  обработчиками; графики — тот же `Svg.renderChart(widget, theme)`, вставленный как
  собственный `<svg viewBox="rect.x rect.y rect.w rect.h">`, спозиционированный CSS-
  абсолютом по тому же `rect` — поэтому график выглядит идентично что на экране, что в
  статичном экспорте, не будучи нарисован дважды разным кодом.
- Типы графиков — закрытый список из пяти: `line`, `bar`, `groupedBar`, `horizontalBar`,
  `donut` (`render/svg.js#renderChart` — единственная точка входа для всех). Алгоритм
  композиции (§10) сегодня производит только `line` и `bar`; `groupedBar`/`horizontalBar`/
  `donut` — часть словаря рендерера для будущих правил композиции или ручной настройки, и
  проверяются во всех 4 темах через QA-стенд `render/gallery.html`.

## 13. Экспорт: кнопка «Поделиться»

Реализовано в [`render/share.js`](render/share.js), кнопка встроена в заголовок дашборда
(`render/dom.js#renderShareButton`), правый верхний угол — как задано в ТЗ.

Механизм: `renderDashboardSvg` для **текущего** (отфильтрованного) состояния → растеризация
через `<img src="blob:...svg">` на `<canvas>` (2×, под ретину) → `canvas.toBlob('image/png')`
→ `navigator.clipboard.write([new ClipboardItem({'image/png': blob})])`; если Clipboard API
недоступен или бросает (нет разрешения, небезопасный контекст) — скачивание файла через
`<a download>`. Состояние кнопки: `Copy image` → `Copied` (или `Downloaded`, если сработал
путь скачивания, — сознательное расхождение с буквальным ТЗ ради честности: пользователь не
должен думать, что файл в буфере обмена, если на самом деле он на диске) → назад к `Copy
image` через 1.6с. Ни модалок, ни меню.

Важная деталь реализации, стоившая одного отладочного прохода: `theme.font.family` — CSS-
стек со встроенными двойными кавычками (`"Segoe UI", ...`). При вставке в HTML через
`innerHTML` лишние кавычки в SVG-атрибуте прощаются мягким HTML-парсером; при загрузке той
же SVG-строки как отдельного XML-документа (`<img src="blob:...">`, ровно то, что происходит
при экспорте) — нет, документ просто не грузится. Все атрибуты в `render/svg.js` теперь
идут через `esc()`, включая корневой `<svg font-family="...">`.

## 14. Excel-адаптер (`/addin`)

Тонкий адаптер поверх уже написанной логики — `/addin` не содержит собственных правил
классификации или композиции, только чтение из Excel и запись в Excel.

### 14.1 Граница тестируемости

Эта среда разработки не имеет доступа к живому Excel-хосту, поэтому код разделён по этому
шву намеренно:

- **Чистая логика** — [`format-bridge.js`](addin/format-bridge.js) (перевод формата ячейки в
  канонический текст), чистая половина [`excel-io.js`](addin/excel-io.js) (`toEngineInput`,
  `inferColumnFormats`) и чистая половина [`dashboard-io.js`](addin/dashboard-io.js) (имена
  фигур/ключей, сборка payload) — не касаются Office.js вообще, полностью протестированы в
  `/tests` (`format-bridge.test.js`, `excel-io.test.js`, `dashboard-io.test.js`) на
  синтетических данных, повторяющих форму `range.values`/`valueTypes`/`numberFormat`.
- **Office.js-вызовы** — `readRangeRaw` (excel-io.js), всё в `dashboard-io.js` после
  комментария "everything below touches context.workbook", и `taskpane.js`'s `excelHost` —
  написаны по документированным паттернам Excel JS API, но не выполнялись ни разу: их
  проверка требует реального Excel (Desktop/Online) и должна пройти отдельно, до релиза.
- **UI/состояние `taskpane.js`** проверено тем не менее полностью — файл спроектирован с
  инъекцией хоста (`excelHost` vs `previewHost`), и `previewHost` подменяет только
  Office.js-вызовы (читает `fixtures/01_sales_timeseries.csv` вместо диапазона, копит
  "сохранённые" дашборды в массиве в памяти вместо `workbook.settings`) — весь остальной код
  (стейт-машина, экраны, скроллинг/масштабирование, тема, фильтры, сортировка,
  список/восстановление) прогнан вручную в браузере через `previewHost` и работает. Так же
  найдены и исправлены две реальные ошибки, которые не всплыли бы без такого прогона: гонка
  порядка `Office.onReady` (см. код) и `showView()`, вызванный после (не до) измерения
  ширины панели для масштабирования — оба чинились именно потому, что было на чём это
  увидеть глазами.
- **Диалоговое окно** (`addin/dashboard-dialog.html/.js`, §14.6) — та же граница: реальный
  `Office.context.ui.displayDialogAsync`/`messageChild`/`messageParent` не проверялся (нет
  Excel-хоста), но вся логика поверх протокола (`addin/dialog-messaging.js`, хендшейк,
  `Dom.mount`/`mountFrozen` с новым `onPlaceOnSheet`, кнопка размещения, весь путь до
  реального `renderPngBase64`/`host.placeDashboard` и обратно) прогнана и работает — подробно
  в §14.6.

### 14.2 Чтение диапазона

`addin/excel-io.js`:
- `values` и `valueTypes` читаются **чанками** (`CONFIG.chunkRows`, по умолчанию 5000
  строк на `context.sync()`) через `range.getCell(start, 0).getResizedRange(n-1, cols-1)` —
  стандартный для Excel JS API приём для больших диапазонов.
- `numberFormat` читается **только для первых `CONFIG.formatSampleRows` строк** (по
  умолчанию 200), как явно потребовано в ТЗ. Формат столбца берётся по первому
  непустому/не-"General" значению в этой выборке (`inferColumnFormats`) — формат почти
  всегда одинаков по всей колонке, поэтому выборка, а не голосование по всем строкам.
- Результат конвертируется в канонический текст (`toEngineInput` →
  `FormatBridge.cellToCanonicalText`) — **тот же формат**, который понимает
  `engine/values.js` при разборе CSV (например, дата → `"2025-01-04"`, процент → `"48.5%"`,
  валюта → `"$1234.56"`). Дальше вызывается ровно `engine.analyzeTable(headers, dataRows,
  ',')` — та же функция, что и для CSV-файла; в движке не появилось ни одной новой строчки
  ради Excel.
- Пустая (`Empty`) и ошибочная (`Error`) ячейка (например `#DIV/0!`) конвертируются в пустую
  строку, а не в буквальный мусор — используется `valueTypes`, а не только `values`.
- Два зафиксированных упрощения (см. комментарии в `format-bridge.js`): система дат 1900
  (легаси-система 1904, старые файлы с Mac, не определяется — Office.js не даёт на это
  прямого API) и потеря времени суток у дат (только дата, что и так всё, что использует
  `engine/aggregate.js`'s бакетинг).

**Обнаруженная и исправленная в процессе ошибка масштаба** (не Excel-специфичная — это баг
самого движка, всплывший именно из требования проверить 200 000 строк): `engine/profile.js`
считал min/max колонки через `Math.min(...values)`/`Math.max(...values)` — спред большого
массива в аргументы вызова переполняет стек заметно раньше 200 000 элементов. Исправлено на
обычный цикл (`minOf`/`maxOf`); тест-регрессия — `tests/profile-scale.test.js`. Синтетический
прогон на 200 000 строк (7 столбцов, дата/текст/число/валюта/процент вперемешку) после
исправления: конвертация в канонический текст — 51мс, `analyzeTable` — 280мс,
`buildLayoutSpec` — 46мс, суммарно **376мс** CPU-времени на всю обработку после того, как
данные уже получены от Excel. Это **не** включает время самого чтения диапазона
(`context.sync()` по сети/IPC к процессу Excel) — вот эту часть можно измерить только в
реальном Excel; `readRangeRaw` возвращает `timing` (`valuesMs`, `formatMs`, `totalMs`)
именно для того, чтобы это было видно в интерфейсе (`build-timing` в`taskpane.html`) при
первом реальном прогоне.

### 14.3 Сценарий «дашборд у человека без аддона»

`addin/dashboard-io.js` + `render/share.js#renderPngBase64`:

1. `renderPngBase64(layoutSpec, theme, columnsByName)` — тот же путь растеризации, что и у
   кнопки «Поделиться» (§13), с текущими применёнными фильтрами (пользователь видит в панели
   именно то, что будет вставлено).
2. `worksheet.shapes.addImage(pngBase64)` — картинка на лист, имя вида
   `DashArchitectDashboard_<timestamp>`.
3. `engine/layout.js#buildStorageSnapshot(layoutSpec, columns)` "замораживает" `layoutSpec`:
   виджет таблицы вместо `rowIndices` (указателя на внешние данные) получает `rows` —
   буквальные значения ячеек той же страницы, что показана на картинке (капа —
   `LAYOUT.table.maxReferenceRows`, как и у самого экспорта). Остальные виджеты уже несут
   все свои числа сами, без изменений. `JSON.stringify` этого снапшота для реального
   датасета — единицы-десятки КБ, комфортно для `workbook.settings`.
4. Снапшот + маппинг столбцов (`{name, role, aggregation}`, на будущее — для правила
   "правка маппинга не пересматривается" из
   [CLAUDE.md](CLAUDE.md#7-пользовательская-правка-маппинга-непобедима), когда появится
   экран ручного маппинга) сохраняются в `context.workbook.settings` под ключом
   `dashArchitect:<имя фигуры>`.
5. Получатель без аддона: обычная картинка, ничего не сломано, ничего не просит установить
   — буквально то, чем PNG и является.
6. Получатель с аддоном: `render/dom.js#mountFrozen(container, layoutSpec, theme)` монтирует
   сохранённый снапшот — **без** повторного чтения листа и без повторной классификации
   столбцов ("без пересчёта" из ТЗ в буквальном смысле). С переездом интерактивного дашборда
   в отдельное диалоговое окно (§14.6) это тоже происходит в диалоге: `layoutSpec`-снапшот
   уезжает туда тем же чанкованным каналом, что и живые данные, просто с `mode: 'frozen'` и
   без `analysis`. Фильтры в этом режиме показаны, но неактивны (нет исходных строк, чтобы
   честно пересчитать агрегаты при изменении фильтра — активная с виду, но не работающая
   кнопка была бы хуже, чем её отсутствие); сортировка таблицы работает — это пересортировка
   уже вложенных в снапшот строк, не обращение к данным. Кнопка «Поделиться» тоже работает в
   этом режиме; кнопки «Place image on sheet» в нём нет — заново размещать нечего и не с чем
   (см. §14.6, `render/dom.js`'s `renderHeader`/`renderPlaceButton`).

### 14.4 Открытие интерактивной версии: клик по картинке

Реализовано двумя путями, и это стоит проговорить прямо: **у Excel JS API нет отдельного
события "по фигуре кликнули"** — это задокументированное ограничение, не то, что можно
обойти более тщательным кодом.

1. **Надёжный путь** — кнопка со списком (`taskpane.html`, иконка в шапке) вызывает
   `dashboard-io.js#listDashboards` (перебор `workbook.settings`, фильтр по префиксу ключа)
   и рисует список; клик "Open" вызывает `mountFrozen`. Работает всегда, независимо от
   платформы.
2. **Эвристика "по клику"** — на `Office.context.document.addHandlerAsync(DocumentSelectionChanged, ...)`
   (то же событие, что уже используется для живого адреса при выборе диапазона) при неудаче
   `context.workbook.getSelectedRange()` (то есть выделено не обычный диапазон — вероятно,
   фигура, но может быть и диаграмма, ошибка или переходное состояние) движок пробует
   `listDashboards`: если сохранённый дашборд ровно один — открывает его; если больше одного
   — открывает список (п. 1) вместо угадывания, какой из них выбрали.

Пункт 2 — лучшее, что можно сделать в рамках документированного API, а не гарантия. Требует
проверки на реальном Excel (Desktop и Web хотя бы) до того, как на него можно будет
полагаться в демо; пункт 1 не требует этой проверки и является страховкой на случай, если
эвристика поведёт себя иначе на каком-то хосте — отсюда решение показывать список, а не
скрывать его как "секретный" путь.

### 14.5 Интерфейс — не content pane

Content add-in (HTML-объект внутри листа, как `reference/manifest-viewer.xml` в демо)
сознательно не реализован — по прямому указанию отложить на потом, а не по техническому
ограничению этой сессии. Task pane (`addin/taskpane.html`) — панель управления: выбор
диапазона, экран маппинга (когда появится), кнопка Generate. Сам интерактивный дашборд с
некоторого момента живёт не в ней, а в отдельном диалоговом окне — см. §14.6.

### 14.6 Диалоговое окно дашборда и протокол сообщений

Task pane узкая (обычно 300–400px) — интерактивный дашборд с исходной шириной канвы 1180px
(`engine/layout.js`'s `LAYOUT.width`) в ней можно только показывать сильно уменьшенным.
Вместо этого `taskpane.js`'s `generate()` открывает дашборд в отдельном окне через
`Office.context.ui.displayDialogAsync(url, { width: 85, height: 85, promptBeforeOpen: false })`
— 85% ширины/высоты экрана, без лишнего запроса на открытие в вебе. Task pane остаётся
открытой и становится чистой панелью управления (§14.5); диалог не может вызывать Office.js
для доступа к книге напрямую (это фундаментальное ограничение модели диалогов Office, а не
недосмотр) — единственное, для чего ему нужен родитель (разместить картинку на листе), он
просит его сделать через сообщение.

**Открывается не более одного диалога одновременно** — `taskpane.js`'s `openDialog(url)`
закрывает предыдущий (`currentDialog.close()`) перед тем, как открыть новый; то же самое окно
используется и для только что сгенерированного дашборда (`mode: 'live'`, `Dom.mount`), и для
восстановленного из `workbook.settings` (`mode: 'frozen'`, `Dom.mountFrozen`) — оба открываются
через `openRestoredDashboard`/`openLiveDashboard`, поэтому пользователь видит один и тот же
интерфейс (масштабирование, переключатель тем) независимо от того, откуда дашборд взялся; это
осознанный выбор, а не побочный эффект — до него `mountFrozen`-версия жила прямо в task pane,
не кликалась и выглядела как отдельная, более бедная возможность, хотя разница на самом деле
только в наличии исходных строк.

**Протокол сообщений** — `addin/dialog-messaging.js`, общий модуль без Office.js/DOM
зависимостей, используется обеими сторонами (`addin/taskpane.js`, `addin/dashboard-dialog.js`),
чтобы формат не мог разъехаться между ними:

- Каждое сообщение — один или несколько конвертов `{kind, requestId, seq, total, payload}`;
  `payload` — часть `JSON.stringify` пересылаемого значения. `createChunkReceiver(kind, onComplete)`
  копит части по `seq` (порядок доставки не важен) и зовёт `onComplete(value, requestId)`, когда
  собраны все `total` частей; `sendChunked(send, kind, value, chunkSize, requestId)` — обратная
  операция. Один и тот же приёмник по `kind`-фильтру можно навесить рядом с другим на один и тот
  же необработанный канал (диалог получает и `data`, и `place-on-sheet-result` через один
  `DialogParentMessageReceived`-обработчик).
- **Рукопожатие**: диалог первым шлёт `{kind:'ready'}` сразу после регистрации своего обработчика
  входящих сообщений; панель ждёт его (`waitForReady`-подобный код в `openLiveDashboard`/
  `openRestoredDashboard`) и только после этого шлёт `data` — иначе первое сообщение уходит в
  пустоту, если диалог ещё не успел подписаться (задокументированная гонка Office Dialog API).
- `data` (панель → диалог): `{mode:'live', analysis, meta}` или `{mode:'frozen', layoutSpec}`.
  `layoutSpec` отдельно от `analysis` **не** пересылается — `render/dom.js#mount` сам вызывает
  `Engine.buildLayoutSpec(analysis, meta)` внутри, и по инварианту детерминизма
  ([CLAUDE.md, п.1](CLAUDE.md#1-детерминизм--это-инвариант-а-не-настройка)) результат у диалога
  будет побайтово тем же, что построила бы панель — присылать его отдельно означало бы второй
  источник истины без выигрыша. Проверено явно: `engine/layout.js#buildLayoutSpec` зависит только
  от `analysis` (`columns`, `rowCount`) и `meta` (`title`, `subtitle`, `activeFilters`, `sort` —
  дефолтятся) — ни темы, ни какого-либо состояния окружения; тема и правда красится отдельно и на
  расположение виджетов не влияет (см. §10-11).
- `place-on-sheet` (диалог → панель): `{canvas, widgets, theme}` — уже посчитанный, с учётом
  текущих фильтров/сортировки набор (та же функция `getSpecForShare`, что отдаёт «Поделиться»),
  плюс id темы (тема не часть `layoutSpec`, диалог её отслеживает сам). Панель ничего не
  пересчитывает — `placeOnSheet(spec)` в `taskpane.js` использует `spec.canvas`/`spec.widgets`
  напрямую, дальше всё как было: `renderPngBase64` → `buildStorageSnapshot` → `host.placeDashboard`.
- `place-on-sheet-result` (панель → диалог): `{ok:true, shapeName}` или `{ok:false, error}`,
  коррелируется с запросом по `requestId`. Кнопка в диалоге (`render/dom.js#renderPlaceButton`)
  показывает «Placing…» → «Placed» / «Could not place: …» — молчащей не остаётся ни в одном
  исходе, как и было потребовано.

**Кнопка размещения — в `render/dom.js`, но без Office.js.** `renderPlaceButton` живёт рядом с
`renderShareButton` в хедере (`renderHeader` теперь принимает второй, необязательный кнопочный
параметр) и вызывается только из `mount()` (не из `mountFrozen()` — см. §14.3). Сама кнопка не
знает про Office.js и не может — этот же модуль используется в `engine/playground.html` и
`render/gallery.html`, где никакого Office-хоста нет. Вместо прямого вызова она принимает
коллбэк `onPlaceOnSheet(spec) → Promise<{ok, shapeName?, error?}>`, который ей передаёт
`mount()`'s пятый параметр (`opts.onPlaceOnSheet`); только `addin/dashboard-dialog.js` (слой,
которому Office.js уже можно) передаёт туда настоящую реализацию, оборачивающую сообщение в
диалог. Та же граница, что уже была у кликов по графику (`onRegionClick`) — рендер остаётся
хост-агностичным, хостовая логика — снаружи.

**Размер чанка — `DEFAULT_CHUNK_SIZE = 700000` символов, выбран консервативно, не измерен на
настоящем транспорте Office-диалога.** В этой среде разработки нет живого Excel/Office-хоста
(та же граница тестируемости, что и у остального `/addin`, см. §14.1) — проверить, при каком
объёме реально падает `Office.context.ui.messageChild`/`messageParent`, физически негде.
Что было сделано вместо этого:
- Сам протокол (`chunkString`/`sendChunked`/`createChunkReceiver`) проверен на многомегабайтных
  синтетических объектах с перемешанным порядком доставки чанков — собирается корректно
  независимо от объёма и порядка; это подтверждает код, а не транспорт.
- Транспорт панели (`openDialogPreview` — обёртка `window.open`+`postMessage` с той же формой,
  что и нативный объект диалога: `messageChild`/`addEventHandler`/`close`) проверен целиком
  вживую через связку "настоящее окно панели + отдельная same-origin реальность (iframe),
  вручную играющая роль диалога" — реальный `window.open`, вызванный из кода аддина по клику,
  в этой браузерной песочнице не создаёт второе окно с рабочей связью `window.opener` (тот же
  класс ограничений автоматизированного браузера, что уже встречался в этой сессии при
  диагностике кликов в task pane), поэтому для проверки именно логики (а не самого браузерного
  `window.open`) использована честная замена на уровне реализации, а не на уровне протокола.
  Так пройден весь путь: рукопожатие → отправка `data` одним/несколькими чанками → размещение
  на лист (реальный `renderPngBase64`/`host.placeDashboard` через `previewHost`) → результат
  обратно, с совпадением `requestId` на каждом шаге.
- **Не проверено и не может быть проверено здесь**: поведение настоящего
  `Office.context.ui.displayDialogAsync`/`messageChild` в реальном Excel — ни факт устойчивой
  доставки больших сообщений, ни момент отказа. Рекомендация: при первом реальном прогоне
  сгенерировать дашборд из объёмного диапазона (десятки тысяч строк) и проверить по отладочной
  панели (`#debug-panel`, временная, добавлена для этой же цели — см. историю диагностики
  кликов в task pane), что все чанки дошли; при отказе — уменьшить `DEFAULT_CHUNK_SIZE` в
  `addin/dialog-messaging.js`.
